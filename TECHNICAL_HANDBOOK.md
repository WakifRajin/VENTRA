## 1. Purpose

This handbook describes how the workspace is organized, how the subsystems connect, which files hold configuration, and how each stack is built and run. Design rationale and results are covered in the project [`README.md`](README.md) and the package documents listed above.

## 2. Workspace Structure

The repository root is a colcon workspace. Source packages are in `src/`. The `build/`, `install/` and `log/` directories are generated by colcon and must not be edited by hand.

### 2.1 Packages

| Package | Origin | Function |
|---|---|---|
| `odom_bridge` | Project | PX4 odometry conversion, external-vision bridge, 3D pose, 3D mapping, frontier exploration, reactive avoidance |
| `shaft_inspection` | Project | SLAM-free shaft perception, mission state machine, mapper, dashboard, bench tools |
| `px4_bringup` | Adapted (MechaMind-Labs) | PX4 SITL, Gazebo, XRCE-DDS agent and bridge bring-up |
| `px4_offboard` | Adapted (MechaMind-Labs) | Velocity Offboard controller, keyboard and joystick teleoperation |
| `rf2o_laser_odometry` | Third party (MAPIRlab) | 2D LiDAR scan-matching odometry |
| `px4_msgs` | Third party (PX4) | PX4 message and service definitions |
| `px4_ros_com` | Third party (PX4) | PX4 to ROS 2 examples and frame-transform helpers |

### 2.2 Files outside `src/`

| Path | Function |
|---|---|
| `drone_gcs.py` | Browser-based process launcher and monitor (FastAPI, port 8080) |
| `web_teleop.py` | Web teleoperation dashboard with MJPEG video (FastAPI, port 8000) |
| `run_cmds/slam.sh` | Sequential start of the localization chain on hardware |
| `run_cmds/drone3d.rviz` | RViz2 configuration for 2D and 3D mapping |
| `slam_params.yaml` | SLAM Toolbox parameters (copy of the package file with `map_update_interval: 5.0`) |
| `shaft_real.yaml` | `shaft_inspection` parameters for the physical vehicle |
| `obstacle_avoidance/` | Standalone MAVSDK front-obstacle back-off test, independent of ROS |
| `scripts/visualize.py`, `scripts/real_visualize.py` | Early PX4 odometry to RViz bridges, superseded by `odom_bridge_node` (see §9) |
| `px4_offboard_updated.zip` | Revised `cmd_vel_offboard_control.py`, `teleop_keyboard.py` and launch file for `px4_offboard` |

## 3. Subsystems

### 3.1 Localization (indoor)

```
PX4 vehicle_odometry ─► odom_bridge_node ─► /odom, TF base_link → laser
/scan ─► rf2o_laser_odometry ─► TF odom → base_link
/scan + TF ─► slam_toolbox ─► /map, TF map → odom
TF map → base_link ─► vision_odom_bridge ─► /fmu/in/vehicle_visual_odometry ─► EKF2
```

The stages must start in order: `odom_bridge_node`, RF2O, SLAM Toolbox, `vision_odom_bridge`. Each stage depends on data from the previous one. Details are in [`src/odom_bridge/README.md`](src/odom_bridge/README.md).

### 3.2 Navigation and exploration

Nav2 (`navigation_launch.py`, parameters in `~/nav2_params.yaml`) plans on the SLAM map. `frontier_explorer` sends `NavigateToPose` goals. Nav2 output on `/cmd_vel` passes through `reactive_avoidance` to `/cmd_vel_safe`, which the Offboard control node converts to PX4 trajectory setpoints.

### 3.3 3D mapping

`pose_3d_node` publishes `map → base_link_3d` using SLAM x, y and yaw together with PX4 z, roll and pitch. `scan_3d_mapper` places each scan in that frame and accumulates a 10 cm voxel map on `/map_3d`. Call `/scan_3d_mapper/save` (`std_srvs/Trigger`) to write a `.ply` file to `~/maps`.

### 3.4 Shaft inspection

A separate stack that replaces the localization and navigation stacks during a shaft flight. `shaft_perception` computes the bore centre from each scan and publishes it to EKF2 as external vision. `shaft_mission` runs the descent and climb state machine and is the only node that commands PX4. Details are in [`src/shaft_inspection/README.md`](src/shaft_inspection/README.md).

### 3.5 Simulation and teleoperation

`px4_bringup/minimal.launch.py` starts PX4 SITL (headless, `gz_x500_gps_denied` in the `hospital` world), the XRCE-DDS agent on UDP port 8888, the Gazebo GUI, QGroundControl and the clock and LiDAR bridges. `px4_offboard` provides keyboard or joystick control through `/offboard_velocity_cmd`. See [`src/ROS2-PX4_Drone_Teleoperation_Using_Joystick/README.md`](src/ROS2-PX4_Drone_Teleoperation_Using_Joystick/README.md).

### 3.6 Ground-control launcher

`drone_gcs.py` starts, stops and monitors every unit from a browser. Units are grouped and started in fixed sequences with settle times between them:

| Group | Units, in start order |
|---|---|
| System | `micro-xrce-agent.service`, `sllidar.service` (systemd) |
| SLAM | `odom_bridge_node`, RF2O, SLAM Toolbox, `vision_odom_bridge` |
| Navigation | Nav2 |
| Explore | `frontier_explorer` |
| Flight | `reactive_avoidance`, obstacle-distance bridge, Offboard control node, web teleoperation |
| 3D mapping | `pose_3d_node`, `scan_3d_mapper`, RViz2 |
| Shaft | `shaft_perception`, `shaft_mapper`, `shaft_dashboard`, `shaft_mission`; bench tools `shaft_preflight`, `shaft_mount_check` |

The launcher enforces two mutual exclusions. Starting one member of a pair stops the other first:

| PX4 input topic | Conflicting units |
|---|---|
| `/fmu/in/vehicle_visual_odometry` | `shaft_perception`, `vision_odom_bridge` |
| `/fmu/in/trajectory_setpoint` | `shaft_mission`, Offboard control node |

Two publishers on one PX4 input topic do not merge. PX4 acts on whichever sample arrived last, and the vehicle alternates between two controllers.

## 4. Interfaces

### 4.1 Coordinate frames

| Frame | Convention | Parent | Publisher |
|---|---|---|---|
| `map` | ENU, SLAM origin | (root) | |
| `odom` | ENU | `map` | `slam_toolbox` |
| `base_link` | FLU | `odom` | `rf2o_laser_odometry` |
| `laser` | FLU | `base_link` | `odom_bridge_node` (static) |
| `base_link_3d` | FLU | `map` | `pose_3d_node` |

PX4 uses NED for the world frame and FRD for the body frame. Conversion matrices are involutory (M · M = I), so the same matrices convert in both directions. External-vision poses use `POSE_FRAME_FRD` because the SLAM map has no north reference.

### 4.2 Principal topics

| Topic | Type | Publisher | Subscribers |
|---|---|---|---|
| `/scan` | `sensor_msgs/LaserScan` | `sllidar_ros2` (vehicle) or Gazebo bridge (SITL) | RF2O, SLAM Toolbox, avoidance, mappers, shaft nodes |
| `/odom` | `nav_msgs/Odometry` | `odom_bridge_node` | RViz, logging |
| `/odom_rf2o` | `nav_msgs/Odometry` | RF2O | (diagnostic) |
| `/map` | `nav_msgs/OccupancyGrid` | SLAM Toolbox | Nav2, `frontier_explorer` |
| `/cmd_vel` → `/cmd_vel_safe` | `geometry_msgs/Twist` | Nav2 → `reactive_avoidance` | Offboard control node |
| `/offboard_velocity_cmd` → `/offboard_velocity_cmd_safe` | `geometry_msgs/Twist` | Teleoperation → `reactive_avoidance` | Offboard control node |
| `/map_3d` | `sensor_msgs/PointCloud2` | `scan_3d_mapper` | RViz |
| `/fmu/in/vehicle_visual_odometry` | `px4_msgs/VehicleOdometry` | `vision_odom_bridge` or `shaft_perception` | PX4 EKF2 |
| `/fmu/out/vehicle_odometry` | `px4_msgs/VehicleOdometry` | PX4 | `odom_bridge_node`, `pose_3d_node` |

The shaft-inspection topics (`/shaft/*`) are listed in [`src/shaft_inspection/README.md`](src/shaft_inspection/README.md) §4.2.

### 4.3 Network ports

| Port | Service |
|---|---|
| 8080 | GCS launcher (vehicle); shaft dashboard (SITL) |
| 8081 | Shaft dashboard (vehicle, set in `shaft_real.yaml`) |
| 8000 | Web teleoperation |
| 8888/UDP | XRCE-DDS agent (SITL only) |

## 6. Build

```bash
source /opt/ros/jazzy/setup.bash
cd ~/px4_ros2_ws
colcon build --symlink-install
source install/setup.bash
```

To rebuild a single stack:

```bash
colcon build --packages-select odom_bridge rf2o_laser_odometry
colcon build --packages-select shaft_inspection
colcon build --packages-select px4_bringup px4_offboard
```

`px4_msgs` must match the PX4 firmware on the vehicle (`release/1.14` for v1.14). A mismatched `px4_msgs` compiles without error but produces misaligned fields or unmatched topics at runtime.

## 7. Operating Procedures

### 7.1 Indoor exploration on the vehicle

1. Power the vehicle. Confirm `micro-xrce-agent.service` and `sllidar.service` are active.
2. Run `python3 ~/px4_ros2_ws/drone_gcs.py` and open `http://<pi-ip>:8080`.
3. Start the SLAM sequence. Confirm `/map` is publishing and the TF tree is complete.
4. Start the Flight sequence. The Offboard control node reads only the avoidance-filtered topics.
5. Take off under manual control and confirm a stable hover.
6. Start Navigation, then Explore. Start 3D mapping if required.
7. On completion, save the 3D map with `ros2 service call /scan_3d_mapper/save std_srvs/srv/Trigger`.

`run_cmds/slam.sh` can replace step 3 when the GCS is not used.

### 7.2 Shaft inspection on the vehicle

Follow [`HARDWARE_GUIDE.md`](src/shaft_inspection/docs/HARDWARE_GUIDE.md) §9 to §13. Stop the SLAM and Flight groups before starting the Shaft group.

### 7.3 Localization chain in SITL

```bash
ros2 launch px4_bringup minimal.launch.py
ros2 launch odom_bridge full_stack_launch.py
```

Expected: `/scan` from the Gazebo bridge, TF `odom → base_link` after about 5 s and `map → odom` after about 8 s, and `/fmu/in/vehicle_visual_odometry` publishing after about 11 s.

### 7.4 Teleoperation in SITL

```bash
ros2 launch px4_bringup minimal.launch.py
ros2 launch px4_offboard keyboard_teleop.launch.py     # or joystick_teleop.launch.py
```

### 7.5 Shaft mission in SITL

```bash
GUI=1 QGC=1 RVIZ=1 MODE=pilot_handover ./run_cmds/shaft_sim.sh
```

See [`src/shaft_inspection/README.md`](src/shaft_inspection/README.md) §6 and §7.

## 8. Diagnostics

| Symptom | Check | Typical cause |
|---|---|---|
| No `/fmu/*` topics | `ros2 topic list \| grep fmu`; agent log | Agent not running; wrong serial device or baud; `UXRCE_DDS_CFG` not set to TELEM2 |
| PX4 topics present but values wrong | `ros2 interface show px4_msgs/msg/VehicleOdometry` | `px4_msgs` branch does not match the firmware |
| SLAM Toolbox idle, no map | `ros2 run tf2_tools view_frames` | `odom → base_link` missing (RF2O not running) or `/scan` absent |
| TF tree flickers or jumps | `ros2 run tf2_ros tf2_echo odom base_link` | Two publishers on one edge (for example `publish_dynamic_tf: true` with RF2O running) |
| EKF2 does not fuse vision | ULog `estimator_status_flags` | `EKF2_EV_CTRL` not set; timestamps out of range; NaN in a required field |
| Vehicle does not respond to Nav2 | `ros2 topic echo /avoidance/status` | Offboard node not remapped to `*_safe` topics; avoidance reporting `NO SCAN` |
| Vehicle alternates between behaviours | GCS log | Two units writing to one PX4 input topic (see §3.6) |

## 9. Known Issues and Open Items

| Item | Impact | Action |
|---|---|---|
| `src/px4_msgs` is version 1.17.0; the vehicle runs PX4 v1.14 | Field or topic mismatch at runtime on the vehicle | Build `px4_msgs` `release/1.14` on the vehicle ([`HARDWARE_GUIDE.md`](src/shaft_inspection/docs/HARDWARE_GUIDE.md) §7.4) |
| Hard-coded `/home/abdazwd` paths (§5.2) | Workspace fails on other accounts | Edit before first run; consider environment variables |
| `full_stack_launch.py` sets `use_sim_time: true` on all nodes | Nodes wait for `/clock` and stall on hardware | Use only in SITL; on hardware use `slam.sh` or the GCS |
| `vision_odom_bridge` stamps messages with the ROS clock | Under sim time PX4 may reject the samples. `shaft_perception` uses the system clock for this reason. | Verify EKF2 acceptance in SITL |
| `scripts/visualize.py` and `scripts/real_visualize.py` publish `odom → base_link` | Conflicts with RF2O | Do not run alongside the localization chain |
| `obstacle_avoidance` scripts default to 115 200 baud | The RPLIDAR C1 uses 460 800 baud | Pass the baud rate explicitly (see [`obstacle_avoidance/readme.md`](obstacle_avoidance/readme.md)) |
| PX4 v1.14 does not export `battery_status` over uXRCE-DDS | Battery-based return budget in `shaft_mission` is inactive on the vehicle | Set `flight_time_budget_s` and `max_depth` in `shaft_real.yaml` |
| `cmd_vel_teleop_v2.py`, `laserscan_to_obstacle_distance.py` and `nav2_params.yaml` are not in the repository | Flight and Navigation groups cannot start on a fresh install | Add to the repository or document their source |
